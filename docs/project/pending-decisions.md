# 未決事項一覧

MVP公開（2026/08/06）までは各担当者がそれぞれの進め方を優先し、
**全体に影響する判断・大規模な改修は公開後にまとめて行う**
（[decisions/0003](../decisions/0003-css-modules-and-feature-directories.md) 適用時期）という方針のもと、公開前に作成された。

MVP公開後の現在も、開発規約・デザイン規約の未決事項を1か所に集める場として継続して使う（development-guidelines.md §26.3）。

作成日：2026-08-05

## 使い方

- 決まったものは行ごと削除する（全体構成に影響するものは、削除前に `docs/decisions/` にADRとして残す。開発規約 §19.2）。本書は「まだ話し合うことが残っている項目」だけを載せる
- 一部だけ決まった論点は、決まった部分を削って残りだけを書く（決定の経緯は残さない。経緯を残したい場合はADR側に書く）
- 個別の機能に閉じる論点は、決定後に各機能のドキュメント（`docs/circle-info/`、`docs/chatbot/`）へ反映する
- 新しく出てきた論点はここに追記する

| C-2 | **画像入稿の運用** | フォーム回答の画像はGoogle Driveの**非公開ファイル**で `<img>` から読めない。現在は表示層で除外しプレースホルダを出している。手順は `public/circles/README.md` に記載済み | ダウンロードと配置の担当者・タイミング。掲載枚数の上限（spec §10-4） |

| C-4 | **`isRecommended` の運用** | 現在は実データ8団体すべて `true`。おすすめ枠の上限は10件（`RECOMMENDED_CIRCLE_LIMIT`）なので、11団体目から選定が必要になる | おすすめに出す基準と、誰が選ぶか |
| C-5 | **`Circle.id` の生成方法** | `sync-circles.ts` は団体名のハッシュ（`circle-d178a0af`）を暫定採用。URLにそのまま出るため読めない（chatbot spec §8 item22） | ローマ字変換 / 連番 / `name-overrides.ts` での手動指定のいずれか。URL変更は既存リンクに影響する |
| C-6 | **CSV列とCircle型の不一致** | (a) 「入会費・年会費など」が1列なのに `fee.admission` / `fee.annual` は別フィールド、(b)「実績」が自由記述1つなのに `achievements` は `{year, content}[]`。現在は暫定格納（chatbot spec §8 item24） | フォームの質問を分割するか、暫定格納を正式仕様にするか |
| C-7 | **フォームに無い項目の更新分担** | `genres` / `summary` / `recommendedFor` / `isRecommended` などに対応するCSV列が無く、circle-info チームの手動補完に依存している（chatbot spec §8 item20） | フォームに列を追加するか、手動運用を正式化するか |
| C-8 | **情報の更新頻度と反映フロー** | 団体側の情報が変わったときの申請〜反映の流れが未定 | 更新申請の受け口と、`npm run sync:circles` の実行タイミング・担当 |
| C-9 | **spec §10 の未決4件** | ①ハンバーガーメニューと「その他」タブの中身 ②ジャンルの正式値（C-1） ③連絡先メールアドレスの公開可否 ④写真の掲載枚数上限（C-2） | 各項目の決定 |

## F. 組織・体制

団体（iFive）としての体制に関わる事項。リポジトリ内の情報だけでは確認できないため、
背景欄の一部は口頭確認が必要（**要確認**と記載）。

| # | 論点 | 背景・現状 | 決めること |
| --- | --- | --- | --- |
| F-2 | **Notion の運用方法の変更** | 現状の使われ方・変更したい点は**要確認**。開発タスクは §4.1 で GitHub Issues / Projects と定めており、Notion と役割が重複しうる | Notion と GitHub で扱う情報の線引き（例：Notion は議事録・ナレッジ、GitHub は開発タスク）。ページ構成と更新の担当・頻度 |
| F-3 | **メンバー管理の方法** | 現在は沼田が**個人的にExcelファイル**で管理している。team 全体からは参照できず、沼田が抜けると引き継げない（属人化） | 個人管理のまま続けるか、団体の共有基盤（Notion 等）へ移すか。移す場合は管理項目・更新責任者・参照権限の範囲。個人情報を含むため、置き場所と共有範囲は慎重に決める |
| F-4 | **営業部と開発部の責務分離** | 部門ごとの責務が明確でなく、開発側が営業・渉外寄りの作業も抱えている（サークル情報のフォーム回収・団体への確認依頼など。C-3・C-7・C-8 が該当） | 両部門の責務の線引き。**開発専門ではない人材の誘致**を進めるか（渉外・データ入稿・広報など、コードを書かない役割の募集）。募集する場合は必要な人数・役割定義・受け入れ方法 |
| F-5 | **インターン試験の分離（開発志望 / 運営志望）** | 現在は志望に関わらず同一の試験を課している（現行内容は**要確認**）。F-4 で開発専門ではない人材を誘致する場合、運営志望者にコーディング中心の試験を課すと本来必要な適性を測れず、応募のハードルにもなる | **開発志望と運営志望で試験を分ける**方針の可否。分ける場合は、それぞれの評価項目（開発＝コーディング・技術理解、運営＝渉外・企画・進行など）、課題の形式と分量、合否の基準、採点担当。志望の申告方法と、途中で志望を変える場合の扱いも決める |
