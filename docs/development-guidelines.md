# Web版 がんちゃんねる 開発規約

> この開発規約をまとめたファイルをAIエージェントに共有して、規約通りに開発してもらうことを目的として作成。

---

## 1. 本規約について

### 1.1 目的

本規約は、複数人でのアプリケーション開発において、以下を実現することを目的とする。

- 開発方法やコードの書き方を統一する
- メンバー間の認識違いを減らす
- Git上での競合や手戻りを防ぐ
- コードの品質と保守性を維持する
- 誰が何を担当しているかを明確にする
- 安全に本番環境へ変更を反映する
- 新しいメンバーが参加しやすい状態を作る

本規約は、メンバーを制限するためのものではなく、チーム内のコミュニケーションを円滑にし、開発を安全に進めるための共通ルールとして使用する。

### 1.2 対象範囲

本規約は、以下の作業を対象とする。

- 要件・仕様の管理
- タスク管理
- Git・GitHubの運用
- コーディング
- コードレビュー
- テスト・動作確認
- ライブラリ・環境変数の管理
- デプロイ
- ドキュメント管理
- AI開発支援ツールの利用

画面の色、余白、フォント、コンポーネントの見た目などについては、別途定めるデザイン規約に従う。

### 1.3 規約の優先度

各規約は、以下の2種類に分類する。

- **必須**：原則として必ず守る
- **推奨**：可能な限り守る

規約を守ることが難しい事情がある場合は、独断で省略せず、チーム内で相談する。

## 4. 情報管理

### 4.1 ツールの役割

情報の重複や分散を防ぐため、各ツールの役割を明確にする。

| 情報 | 管理場所 |
| --- | --- |
| 正式な開発タスク | GitHub Issues |
| タスクの進捗状況 | GitHub Projects |
| 要件・仕様書 | Notionまたは指定ドキュメント |
| デザイン | Figmaまたは指定ツール |
| コード | GitHub |
| 日常的な連絡・相談 | DiscordまたはSlack |
| 重要な意思決定 | Notion、Issue、議事録 |
| 不具合報告 | GitHub Issues |

チャット上の会話だけで、重要な仕様や決定事項を完結させない。

### 4.2 進捗共有

各メンバーは、作業状況がほかのメンバーから確認できる状態にする。

最低限、以下を更新する。

- Issueの担当者
- Issueのステータス
- 作業中のブランチ
- Pull Requestの状態
- 作業上の問題や不明点

長期間作業が止まる場合や、予定より遅れる場合は、早めにチームへ共有する。

## 5. タスク・Issue管理規約

### 5.1 基本ルール

**必須**

- 原則として、コードを変更する前にIssueを作成する
- Issueごとに担当者を設定する
- Issueには完了条件を記載する
- 仕様が不明確な場合は、実装前に確認する
- 発見した不具合は口頭だけで済ませず、Issueとして残す
- 作業完了後はIssueを更新または終了する

軽微な誤字修正など、Issueを作成する必要がないとチームで合意した作業は例外とする。

### 5.2 Issueの記載項目

Issueには、原則として以下を記載する。

```md
## 概要

何を実装・修正するのかを記載する。

## 目的

なぜこの作業が必要なのかを記載する。

## 実装内容

- 実装する内容1
- 実装する内容2
- 実装する内容3

## 完了条件

- [ ] 条件1
- [ ] 条件2
- [ ] 条件3

## 関連資料

- デザイン：
- 仕様書：
- 関連Issue：

## 補足

実装時の注意点や、まだ決まっていない事項を記載する。
```

### 5.3 Issueタイトル

Issueタイトルは、内容が具体的に分かる名称にする。

良い例：

```text
ユーザー登録フォームを実装する
スマートフォン表示でヘッダーが崩れる問題を修正する
団体詳細ページに活動実績欄を追加する
```

避ける例：

```text
登録機能
修正
画面を作る
バグ対応
```

### 5.4 タスクの大きさ

1つのIssueが大きすぎる場合は、複数のIssueに分割する。

目安として、以下のいずれかに該当する場合は分割を検討する。

- 複数の独立した機能を含む
- 担当者が複数人になる
- 完了までに長期間かかる
- フロントエンドとバックエンドで作業が明確に分かれる
- Pull Requestの変更量が大きくなる

## 6. Git・ブランチ運用規約

### 6.1 使用するブランチ

小規模開発では、原則として以下の構成を使用する。

- `main`：動作確認済みのコードを管理する
- 作業ブランチ：各機能や修正を実装する

原則として、`develop`ブランチは使用しない。

必要性が生じた場合は、チーム内で相談して追加する。

### 6.2 mainブランチ

**必須**

- `main`ブランチは常に動作可能な状態を維持する
- `main`ブランチへの直接pushは禁止する
- `main`への変更はPull Requestを通して行う
- 動作確認やレビューが完了していないコードをマージしない

### 6.3 ブランチ名

ブランチ名は、以下の形式とする。

```text
作業種別/Issue番号-作業内容
```

例：

```text
feature/12-user-signup
fix/24-mobile-header
docs/31-update-readme
refactor/42-user-service
test/53-add-login-test
chore/61-update-eslint
```

使用する作業種別は以下とする。

| 種別 | 用途 |
| --- | --- |
| `feature` | 新機能の追加 |
| `fix` | 不具合修正 |
| `docs` | ドキュメント修正 |
| `refactor` | 機能を変更しないコード整理 |
| `test` | テストの追加・修正 |
| `chore` | 設定、ライブラリ、環境整備 |
| `style` | CSSや表示上の修正 |

### 6.4 作業開始時の手順

作業開始前に、最新の`main`ブランチを取得する。

```bash
git switch main
git pull origin main
```

作業ブランチを作成する。

```bash
git switch -c feature/12-user-signup
```

すでに作業ブランチが存在する場合は、新しく作成せず既存ブランチへ移動する。

### 6.5 競合を防ぐためのルール

- 作業開始時に担当するIssueを明確にする
- 同じファイルを複数人で大きく変更する場合は事前に相談する
- 長期間ブランチを放置しない
- 定期的に`main`の変更を取り込む
- コンフリクトが発生した場合は、関係する担当者と確認しながら解消する
- 他人が書いた処理を、意図を確認せず削除しない

## 7. コミット規約

### 7.1 コミットの単位

**必須**

- 1つのコミットには、原則として1つの意味を持たせる
- 無関係な変更を同じコミットに含めない
- 動作しない状態を長期間コミットしない
- デバッグ用ファイルや不要な生成物をコミットしない

例えば、以下の変更は可能な限り別のコミットにする。

- 新機能の追加
- CSSの修正
- READMEの更新
- 不具合の修正
- ライブラリの更新

### 7.2 コミットメッセージ

コミットメッセージは、以下の形式とする。

```text
変更種別: 変更内容
```

例：

```text
feat: ユーザー登録フォームを追加
fix: モバイル表示でヘッダーが崩れる問題を修正
docs: READMEに環境構築手順を追加
refactor: API通信処理を共通関数に分離
test: ログイン処理のテストを追加
chore: ESLintの設定を更新
style: 団体詳細ページの余白を調整
```

### 7.3 使用する変更種別

| 種別 | 内容 |
| --- | --- |
| `feat` | 新機能 |
| `fix` | 不具合修正 |
| `docs` | ドキュメント |
| `style` | 見た目やフォーマット |
| `refactor` | リファクタリング |
| `test` | テスト |
| `chore` | 設定、ライブラリ、環境整備 |

### 7.4 避けるコミットメッセージ

以下のように、変更内容が分からないメッセージは使用しない。

```text
修正
更新
作業
いろいろ変更
完成
一旦コミット
```

## 8. Pull Request規約

### 8.1 基本ルール

**必須**

- `main`への変更はPull Requestを通す
- Pull Requestには関連Issueを記載する
- 作成者以外のメンバーがレビューする
- 指摘への対応が完了してからマージする
- 画面変更がある場合はスクリーンショットを添付する
- Pull Request作成前に、最低限の動作確認を行う
- 1つのPull Requestに複数の無関係な機能を含めない

### 8.2 Pull Requestの大きさ

Pull Requestは、レビュー可能な大きさに抑える。

**推奨**

- 1つの機能または1つの修正に限定する
- 大きな変更は複数のPull Requestに分割する
- 変更ファイル数やコード量が多くなる場合は事前に共有する
- 数百行を大きく超える場合は分割を検討する

自動生成ファイルやlockファイルは、変更量の目安から除外してよい。

### 8.3 Pull Requestテンプレート

```md
## 概要

このPull Requestで行った変更を簡潔に記載する。

## 関連Issue

close #

## 変更内容

-
-
-

## 確認方法

1.
2.
3.

## 動作確認

- [ ] ローカル環境で起動できる
- [ ] 変更した機能が正常に動作する
- [ ] 既存機能が壊れていない
- [ ] Lintエラーがない
- [ ] ビルドが成功する
- [ ] 不要なログを削除した
- [ ] PC表示を確認した
- [ ] スマートフォン表示を確認した

## スクリーンショット

画面変更がある場合に添付する。

## レビューしてほしい点

特に確認してほしい部分や、不安な点を記載する。

## 補足

実装上の判断、未対応事項、今後の課題などを記載する。
```

### 8.4 Draft Pull Request

実装途中でも、以下の場合はDraft Pull Requestを作成してよい。

- 実装方針について相談したい
- 早い段階でレビューを受けたい
- 大きな変更の進捗を共有したい
- ほかのメンバーと連携する必要がある

Draft状態のPull Requestは、原則としてマージしない。

## 9. コードレビュー規約

### 9.1 レビューの目的

コードレビューは、実装者の能力やミスを責めるためではなく、以下を目的として行う。

- 要件を満たしているか確認する
- 不具合を早期に発見する
- コードを理解しやすくする
- 知識をチーム内で共有する
- 特定のメンバーだけが理解している状態を防ぐ
- セキュリティ上の問題を防ぐ

### 9.2 レビュー項目

レビュアーは、主に以下を確認する。

**仕様・機能**

- Issueの目的を満たしているか
- 完了条件を満たしているか
- 想定どおりに動作するか
- エラー時の処理が考慮されているか

**コード品質**

- 変数名や関数名が分かりやすいか
- 処理が必要以上に複雑になっていないか
- 同じ処理が重複していないか
- 1つの関数やコンポーネントに責務が集中していないか
- 不要なコードが残っていないか
- ほかのメンバーが理解できるか

**影響範囲**

- 既存機能を壊していないか
- APIやデータベースへの影響がないか
- 画面表示に意図しない変更がないか
- セキュリティ上の問題がないか

### 9.3 レビューコメントの分類

レビューコメントには、可能な限り分類を付ける。

```text
【必須】
マージ前に修正が必要な内容

【提案】
必須ではないが、よりよい実装方法の提案

【質問】
実装意図や仕様について確認したい内容

【軽微】
誤字、表記、命名などの小さな指摘

【参考】
今後役立つ情報や知識の共有
```

### 9.4 コメントの書き方

指摘する場合は、可能な限り理由を添える。

避ける例：

```text
ここを直してください。
この書き方はよくないです。
```

推奨例：

```text
【提案】
この処理は別の画面でも利用する可能性があるため、
共通関数に分けると再利用しやすくなると思います。
```

### 9.5 レビュー対応

Pull Request作成者は、レビューコメントに対して以下のいずれかを行う。

- 修正する
- 質問に回答する
- 修正しない理由を説明する
- 別Issueで対応することを提案する

コメントを確認せずに解決済みにしない。

### 9.6 レビュー期限

**推奨**

- レビュー依頼を受けた場合は、可能な限り1営業日以内に確認する
- すぐに確認できない場合は、その旨を共有する
- 緊急性の高いPull Requestは、チャットでも連絡する

## 10. コーディング規約

### 10.1 基本方針

**必須**

- プロジェクトで設定されたESLintやPrettierに従う
- Lintエラーを残したままマージしない
- 使用していない変数、関数、importを残さない
- デバッグ用のコードやログを残さない
- APIキーやパスワードをコードに直接書かない
- 意味を理解していないコードをそのまま使用しない

### 10.2 命名規則

原則として、以下の命名規則を使用する。

| 対象 | 規則 | 例 |
| --- | --- | --- |
| 変数 | camelCase | `userName` |
| 関数 | camelCase | `calculateTotalPrice` |
| Reactコンポーネント | PascalCase | `UserProfile` |
| 型・インターフェース | PascalCase | `UserData` |
| 定数 | UPPER_SNAKE_CASE | `MAX_LOGIN_ATTEMPTS` |
| ファイル | プロジェクト内で統一 | `user-profile.tsx`など |

良い例：

```ts
const userName = "Numata";

function calculateTotalPrice() {
  // 処理
}

const MAX_LOGIN_ATTEMPTS = 5;

function UserProfile() {
  return <div />;
}
```

避ける例：

```ts
const a = "Numata";
const data2 = [];
const tmp = {};
function aaa() {}
```

ループ処理など、役割が明確な場合は`i`などの短い変数名を使用してよい。

### 10.3 関数・コンポーネント

**推奨**

- 1つの関数には、可能な限り1つの責務を持たせる
- 長すぎる関数は分割を検討する
- 複雑な条件分岐は、関数への切り出しを検討する
- 同じ処理を複数箇所へコピーしない
- Reactコンポーネントが大きくなりすぎた場合は分割する
- UI表示とデータ取得処理の分離を検討する

### 10.4 TypeScript

TypeScriptを使用する場合は、以下を原則とする。

- `any`は原則として使用しない
- APIレスポンスやpropsには型を定義する
- 型が不明な値には、必要に応じて`unknown`を使用する
- 型エラーを無理に無効化しない
- `@ts-ignore`を使用する場合は理由をコメントする

### 10.5 コメント

コメントには、コードを読めば分かる内容ではなく、主に以下を書く。

- なぜその実装にしたのか
- 仕様上の制約
- 一見すると不要に見える処理の理由
- 外部サービスやライブラリ固有の注意点
- 将来的な改善事項

避ける例：

```ts
// ユーザー一覧を取得する
const users = await fetchUsers();
```

推奨例：

```ts
// APIへの負荷を抑えるため、初期表示では最大20件に制限する
const users = await fetchUsers({ limit: 20 });
```

### 10.6 TODOコメント

一時的に未対応事項を残す場合は、内容と関連Issueを記載する。

```ts
// TODO: #42 ページネーション対応時に取得件数を変更する
```

可能な限り、TODOコメントだけで管理せずIssueも作成する。

## 11. フォーマッター・Lint規約

### 11.1 使用ツール

プロジェクトでは、原則として以下を使用する。

- ESLint
- Prettier
- TypeScriptの型チェック

必要に応じて、以下の導入を検討する。

- Stylelint
- Husky
- lint-staged
- GitHub Actions

### 11.2 自動整形

コードの空白、改行、引用符、末尾のセミコロンなどは、原則としてPrettierの設定に従う。

個人の好みで整形ルールを変更しない。

### 11.3 設定変更

ESLintやPrettierの設定を変更する場合は、以下をPull Requestに記載する。

- 変更理由
- 影響範囲
- 既存コードへの影響
- 新しいルールへの対応方法

## 12. ディレクトリ・ファイル管理

### 12.1 基本ルール

- 同じ役割のファイルは同じディレクトリに配置する
- プロジェクト内の既存構成に従う
- 独自の判断で大規模なディレクトリ変更を行わない
- 使用していないファイルを残さない
- 自動生成ファイルを手動で編集しない
- 大規模な構成変更は、実施前にチームへ相談する

### 12.2 ファイル名

ファイル名の規則は、技術構成に合わせて統一する。

例：

```text
components/
  user-profile.tsx

hooks/
  use-user.ts

services/
  user-service.ts

types/
  user.ts
```

Reactコンポーネントのファイル名をPascalCaseにする場合は、プロジェクト全体で統一する。

### 12.3 共通コンポーネント

ボタン、入力欄、モーダルなど、複数画面で使用するUIは共通コンポーネント化を検討する。

ただし、1回しか使用しないものを過度に共通化しない。

共通コンポーネントの見た目や利用方法は、別途定めるデザイン規約に従う。

## 13. ライブラリ管理規約

### 13.1 ライブラリ追加

新しいライブラリを追加する前に、以下を確認する。

- 標準機能で実現できないか
- すでに同じ目的のライブラリが入っていないか
- 現在も保守されているか
- ライセンス上の問題がないか
- プロジェクトの規模に対して過剰ではないか
- セキュリティ上の問題がないか

主要なライブラリを追加する場合は、事前またはPull Request上で共有する。

### 13.2 重複禁止

同じ目的のライブラリを複数導入しない。

例：

- 日付処理に`date-fns`と`dayjs`を併用しない
- HTTP通信に`fetch`と`axios`を無計画に混在させない
- 複数のUIライブラリを無計画に導入しない

### 13.3 lockファイル

以下のlockファイルはGitで管理する。

- `package-lock.json`
- `pnpm-lock.yaml`
- `yarn.lock`
- その他、使用するパッケージ管理ツールのlockファイル

チーム内では、原則として同じパッケージ管理ツールを使用する。

### 13.4 ライブラリ更新

大規模なバージョンアップは、通常の機能追加と分けて行う。

更新時は以下を確認する。

- 破壊的変更の有無
- ビルドが成功するか
- 既存機能が動作するか
- 設定ファイルの変更が必要か
- セキュリティ上の修正が含まれているか

## 15. 環境変数・秘密情報

### 15.1 必須ルール

- `.env`をGitへ追加しない
- APIキーをコードに直接書かない
- パスワードをコードやIssueに記載しない
- アクセストークンをチャットへ貼り付けない
- 個人情報をテストデータとして使用しない
- 秘密情報をスクリーンショットに写さない

### 15.2 .env.example

必要な環境変数は、`.env.example`に記載する。

```env
DATABASE_URL=
NEXT_PUBLIC_API_BASE_URL=
AUTH_SECRET=
```

`.env.example`には、実際のAPIキーやパスワードを記載しない。

### 15.3 秘密情報を公開した場合

秘密情報を誤ってGitHubへpushした場合は、ファイルを削除するだけでは不十分である。

以下を実施する。

1. チームへ直ちに共有する
2. 該当するAPIキーやパスワードを無効化する
3. 新しいキーやパスワードを発行する
4. Git履歴からの削除が必要か確認する
5. 再発防止策を検討する

## 16. データベース・API規約

### 16.1 データベース変更

データベース構造を変更する場合は、以下を共有する。

- 変更するテーブル
- 追加・削除するカラム
- 既存データへの影響
- APIへの影響
- マイグレーション方法
- 本番環境への適用手順

本番環境のデータベースを、個人の判断で直接変更しない。

### 16.2 マイグレーション

- マイグレーションファイルはGitで管理する
- 既存のマイグレーションを無断で書き換えない
- 本番適用前に開発環境で確認する
- データ消失の可能性がある変更は事前に共有する

### 16.3 API変更

APIのURL、リクエスト、レスポンス形式を変更する場合は、利用する側の担当者へ共有する。

以下を明確にする。

- HTTPメソッド
- エンドポイント
- リクエスト形式
- レスポンス形式
- エラー形式
- 認証の有無
- 変更前後の差分

フロントエンドとバックエンドで認識が分かれないように、可能な限りAPI仕様を文書化する。

## 17. テスト・動作確認規約

### 17.1 Pull Request作成前の確認

Pull Requestを作成する前に、以下を確認する。

**必須**

- [ ] アプリが起動する
- [ ] 変更した機能が正常に動作する
- [ ] 既存機能が壊れていない
- [ ] Lintエラーがない
- [ ] 型エラーがない
- [ ] ビルドが成功する
- [ ] ブラウザコンソールに不要なエラーがない
- [ ] デバッグ用ログを削除した
- [ ] 不要なファイルを含めていない
- [ ] 秘密情報を含めていない

**画面変更がある場合**

- [ ] PC表示を確認した
- [ ] スマートフォン表示を確認した
- [ ] 極端に長い文章でも崩れない
- [ ] 画像が表示されない場合も考慮されている
- [ ] ボタンやリンクが操作できる
- [ ] デザイン規約に反していない

### 17.2 実行コマンド

使用する技術に応じて、以下のコマンドを実行する。

```bash
npm run lint
npm run type-check
npm run test
npm run build
```

プロジェクトに存在しないコマンドは省略してよい。

### 17.3 テストコード

テストを導入する場合は、特に以下を優先する。

- 認証処理
- 金額や数値の計算
- 入力値の検証
- データ変換処理
- 重要なAPI
- 不具合が発生しやすい処理
- 過去に不具合が発生した処理

すべてを自動テストするのではなく、重要度に応じて導入する。

## 20. AI開発支援ツールの利用規約

本規約では、ChatGPT、Claude Code、GitHub Copilot、CodexなどをAI開発支援ツールとする。

### 20.1 利用可能な用途

AIツールは、以下の用途で利用してよい。

- コードの作成補助
- 不具合原因の調査
- リファクタリング案の作成
- テストコードの作成
- ドキュメントの作成
- コードレビューの補助
- 技術調査
- エラーメッセージの解釈

### 20.2 必須ルール

- AIへ秘密情報を入力しない
- 個人情報を入力しない
- APIキーやパスワードを入力しない
- AIが生成したコードは、利用者本人が内容を確認する
- 動作を理解できないコードをそのままマージしない
- AI生成コードも通常のコードレビュー対象とする
- 存在しないライブラリやAPIを使用していないか確認する
- ライセンス上問題のあるコードをコピーしない
- AIの回答を、公式ドキュメントより優先しない

### 20.3 AI生成コードの責任

AIが生成したコードであっても、コミットしたメンバーが内容に責任を持つ。

「AIが生成したため分からない」という状態でPull Requestを提出しない。

### 20.4 AIによる大規模変更

AIツールに大規模なコード変更を依頼する場合は、以下を守る。

- 作業前にGitの状態を保存する
- 変更対象を明確に限定する
- 変更内容をファイルごとに確認する
- 不要な変更が含まれていないか確認する
- Lint、ビルド、テストを実行する
- 一度に巨大なPull Requestを作らない

### 21.2 優先度

| 優先度 | 状態 |
| --- | --- |
| 緊急 | アプリ全体が利用できない、情報漏えいの可能性がある |
| 高 | 主要機能が利用できない |
| 中 | 一部機能に問題があるが回避方法がある |
| 低 | 軽微な表示崩れ、誤字、改善要望 |

## 22. 禁止事項

以下の行為を禁止する。

- `main`ブランチへの直接push
- 秘密情報のコミット
- 他人のコードを無断で大幅に削除すること
- レビューを通さず本番反映すること
- 仕様を確認せず独断で変更すること
- 理解していないAI生成コードをマージすること
- 個人情報をテストデータとして使用すること
- チームへ共有せず主要ライブラリを変更すること
- 動作確認をせずPull Requestをマージすること
- 本番データベースを個人の判断で直接操作すること
- IssueやPull Request上でパスワードを共有すること

## 23. 開発の基本フロー

各メンバーは、原則として以下の手順で作業する。

1. 仕様書やデザインを確認する
2. Issueを作成または担当する
3. Issueの目的と完了条件を確認する
4. 最新の`main`ブランチを取得する
5. Issue用の作業ブランチを作成する
6. 実装する
7. 自分で動作確認する
8. Lint、型チェック、ビルド、テストを実行する
9. コミットする
10. リモートリポジトリへpushする
11. Pull Requestを作成する
12. レビューを依頼する
13. 指摘に対応する
14. 承認後にマージする
15. Issueを終了する
16. 必要に応じてドキュメントを更新する

## 24. Definition of Done

Issueが完了したと判断する基準を、Definition of Doneとして定める。

以下をすべて満たした場合に、原則として完了とする。

- [ ] Issueの完了条件を満たしている
- [ ] 実装内容が仕様書と一致している
- [ ] デザイン規約に従っている
- [ ] ローカル環境で正常に動作する
- [ ] 既存機能を壊していない
- [ ] Lintエラーがない
- [ ] 型エラーがない
- [ ] ビルドが成功する
- [ ] 必要なテストが完了している
- [ ] Pull Requestがレビューされている
- [ ] レビュー指摘への対応が完了している
- [ ] 必要なドキュメントを更新している
- [ ] 秘密情報や不要なコードを含んでいない
- [ ] `main`ブランチへマージされている

## 25. 例外対応

緊急時など、本規約どおりに進めることが難しい場合は、以下を実施する。

1. 例外対応が必要な理由を共有する
2. プロジェクト責任者または開発リーダーの了承を得る
3. 対応内容を記録する
4. 対応後に通常のレビューや確認を行う
5. 同様の問題が発生しないように見直す

緊急対応であっても、秘密情報や個人情報の管理規則は省略しない。

## 26. 規約の見直し

### 26.1 見直し時期

本規約は、以下のタイミングで見直す。

- 開発開始から1〜2週間後
- 最初のリリース後
- 同じ問題が複数回発生したとき
- 新しいメンバーが参加したとき
- 使用技術や開発体制が変わったとき
- 規約が開発の妨げになっているとき

### 26.2 見直し観点

- 守られていない規約はあるか
- 規約が分かりにくくないか
- 不要な規約はないか
- 自動化できる規約はないか
- 新しく追加すべき規約はないか
- 特定のメンバーだけに負担が集中していないか
- 実際の開発方法と規約が一致しているか

規約を増やすだけでなく、不要な規約を削除することも検討する。

## 27. 初期段階で特に優先する規約

プロジェクト開始時は、最低限以下を徹底する。

1. 作業前にIssueを確認する
2. `main`ブランチへ直接pushしない
3. Issueごとに作業ブランチを作る
4. Pull Requestを通してマージする
5. 1人以上がコードレビューを行う
6. マージ前にLintとビルドを確認する
7. `.env`やAPIキーをGitHubへ公開しない
8. 画面変更時はスクリーンショットを添付する
9. 重要な仕様変更は文章として残す
10. AI生成コードも内容を理解してから使用する
