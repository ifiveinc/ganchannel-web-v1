# 0005. タスク管理はGitHub Issues + GitHub Projects + Notionを継続する（Jira/Confluenceは見送り）

- 日付: 2026-09-03
- ステータス: 採用

## 背景

開発規約 §4.1・§5・§6.3は「正式な開発タスクはGitHub Issues、進捗管理はGitHub Projects」を前提に書かれていたが、pending-decisions.md A-4で指摘されていたとおり、実際にはIssueがほとんど使われておらず、ブランチ名にもIssue番号が入っていない状態だった（規約と運用の乖離）。

この解消にあたり、GitHub Issues/Projectsを実際に運用に乗せる案に加えて、企業で実際に使われるJira＋Confluenceを導入する案が挙がった。チーム内で複数の意見を出し合い、以下の論点を検討した。

- **Jira無料プランの制約**：利用ユーザー数が10までに制限され、プロジェクトが増えた場合にJiraサイトを使い分ける非効率が生じる懸念
- **折衷案（がんちゃんねる限定でJira＋Confluenceを試験導入し、他プロジェクト〈iFive-HP等〉はGitHub Projectsのまま比較する）**も検討したが、iFiveの少人数体制では複数プロジェクトを同じメンバーが並行して担当するため、対象プロジェクトを絞っても実質的にキャッチアップ負荷は分散しきれないと判断した
- **教育的価値**：目的は「大規模開発で使われるBacklog/Sprint/Epicなどの考え方を体験すること」だが、がんちゃんねるのような小規模プロジェクトではその必要性が薄く、体験の質も上がりにくい。マイレージ可視化アプリのような、ある程度規模のある案件で改めて導入した方が、必要性を感じながら学べるため定着しやすい
- **GitHub Issues/Projectsも大半のメンバーが未経験**という指摘もあったが、GitHub自体は既にコード管理で全員が使っており、新規に覚えるのはProjectsのボード機能の使い方のみで済む。Jira＋Confluenceは、それに加えて別プラットフォームのアカウント・通知・権限管理という運用コストが追加で発生する。同程度の学習コストを払うなら、必要性の高いタイミング（学祭後、規模の大きい案件）に払う方がリターンが大きい

## 決定

- 正式な開発タスク・不具合報告は**GitHub Issues**、進捗管理は**GitHub Projects**で行う（開発規約の記載どおりに戻す）
- 要件・仕様書・重要な意思決定の記録先は変更しない（`docs/`配下を正本とし、Notionは外部共有用途で使う従来どおりの運用）
- Jira＋Confluenceの導入は**今回は見送る**。学祭対応が落ち着いた後、またはマイレージ可視化アプリのような規模の大きい案件が始まるタイミングで改めて検討する
- GitHub Issues/GitHub Projectsを名実ともに定着させるため、ボードの実際の構築とメンバー向けオンボーディングをfestival-issues.md 0-1で実施する

## 理由

- ツールを変えても、導入時にきちんとオンボーディングしなければ同じ「定着しない」問題が再発する。今回の根本原因は運用の定着不足であり、ツールの欠陥ではなかった
- 学祭（10/16）対応で開発リソースが逼迫している時期に、新しいプラットフォームのキャッチアップコストを重ねるのは負担が大きい
- 大規模開発の考え方を学ぶという目的は、それを必要とする規模の案件に当てた方が実感を伴って定着する

## 影響

- 開発規約 §2・§4.1・§5・§6.3は変更なし（元のGitHub Issues/Projects/Notion前提のまま）
- team-structure.md・festival-issues.mdのJira関連の記載は元に戻した
- pending-decisions.md A-4（タスク管理方法の検討）は本ADRの決定をもって解消し、該当行を削除した
- GitHub Projectsのボード作成・メンバー向けオンボーディングをfestival-issues.md 0-1のタスクに追加した
